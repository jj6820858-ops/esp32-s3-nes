# 从实际源码理解 ESP32 NES 掌机

这份工程仍然使用 Retro-Go / Nofrendo。红白机 CPU、PPU、APU 和 mapper 均保留
开源实现；自己的代码负责把它们接到实战派开发板。

板级驱动、应用切换和 NES 核心入口现已补充中文源码注释。阅读时先看文件/函数头的
职责说明，再看数据单位、初始化顺序、缓冲区归属和错误路径；版权及许可证保留原文。

## 推荐阅读顺序

用 VS Code 打开 [SZPI-NES.code-workspace](../SZPI-NES.code-workspace)，IDF 工程目录是 `retro-core`。
按 `Ctrl+P` 输入路径，`Ctrl+Shift+F` 搜函数名，按下面顺序读：

1. [config.h](../components/retro-go/targets/szpi-esp32s3/config.h)：先看屏幕、触摸、TF、声音的引脚。
2. [szpi_board.c](../components/retro-go/targets/szpi-esp32s3/szpi_board.c)：I2C 初始化 → PCA9557，保持 LCD CS 为高 → 检查触摸芯片。
   接着读 [szpi_st7789.h](../components/retro-go/drivers/display/szpi_st7789.h)：SPI 就绪后才选中、复位及初始化 LCD。
3. [szpi_storage.c](../components/retro-go/targets/szpi-esp32s3/szpi_storage.c)：SDMMC 初始化 → 读取整卡第 0 扇区 → 识别已有分区。
4. [szpi_partition.c](../components/retro-go/targets/szpi-esp32s3/szpi_partition.c)：解析 MBR / FAT 启动扇区，选择最大的有效 FAT32 分区。
5. [applications.c](../launcher/main/applications.c) 的 `application_start()`：保存 ROM 路径、选择应用分区后重启。
6. [main.c](../retro-core/main/main.c)：根据配置进入 `nes_main()`。
7. [main_nes.c](../retro-core/main/main_nes.c)：读取 ROM → 更新手柄 → 模拟一帧 → 显示和音频提交。
8. [nes.c](../retro-core/components/nofrendo/nes/nes.c)：CPU 执行与 PPU 扫描线怎样配合。

## 为什么三个盘符只挂载一个

E/F/G 是 Windows 分配的盘符，ESP32 看不到盘符，而是读取 MBR 的起始扇区和长度。
本程序先读取各分区的 FAT BPB，核对容量、每簇扇区数、FAT 表及根目录参数，再
选择最大的 FAT32 区域。前面的 BIN/SDCARD 小分区继续保留。

假设游戏分区起始扇区是 2097152，则：

```text
FatFs 请求游戏分区内第 100 扇区
                 ↓ 加起始扇区偏移
SDMMC 实际读取整卡第 2097252 扇区
```

每次读写均核对 `sector + count` 没有超过该分区长度。程序没有调用格式化、
重新分区或整卡擦除接口。TF 卡的原始 MBR 和前两个分区不经过文件系统写入路径。

## Flash、PSRAM 与 TF 的分工

- ESP32 Flash：Bootloader、launcher、retro-core 固件。
- RAM / PSRAM：读入的 ROM、模拟器状态、图像和音频数据。
- TF 卡的数据分区：`.nes` 游戏、Retro-Go 配置、存档和封面。

应用切换修改的是 ESP32 Flash 的启动记录；选择 TF 分区修改的是程序内的扇区
映射，两者是不同层次，不能把 TF 的 MBR 与 ESP32 的 partitions.csv 混淆。

`.nes` 内是 6502 游戏程序和图形数据，由模拟器解释执行；ESP32 本身执行的是
编译后的 Xtensa 固件。复制游戏到 TF 通常不需要重新烧录。
[rom_loadfile()](../retro-core/components/nofrendo/nes/rom.c) 用 `malloc()` / `fread()`
读入 ROM，并不是每执行一条游戏指令就访问 TF。

[sdkconfig](../components/retro-go/targets/szpi-esp32s3/sdkconfig) 让 PSRAM 参与通用堆分配，
实际分配位置受大小、配置和空闲情况影响，不能认为所有数据都在 PSRAM。
[rg_alloc()](../components/retro-go/rg_utils.c) 还能指定内存能力：`MEM_FAST` 请求片内内存，
`MEM_SLOW` 请求 PSRAM，部分请求允许回退；`MEM_DMA` 请求 DMA 可用内存。
当前 NES 的两个图像面请求 `MEM_FAST`，LCD 的中转缓冲请求 `MEM_DMA`。

## 测试 ROM 怎么用

程序首次挂载成功会创建 `/roms/nes/SZPI-Controls.nes`；已有同名文件不会覆盖。
它由 `tools/make_nes_demo.py` 生成，包含自己编写的 6502 程序和图案。

- 方向键：移动小图案。
- A：发出方波音。
- B：改变小图案颜色。
- M / BOOT：Retro-Go 游戏菜单，能测试存档、加载和返回菜单。

## 用串口辅助调试

COM5，115200 波特率。单个字符可直接发送，不需要回车：

| 字符 | 动作 |
|---|---|
| `?` | 显示调试命令 |
| `g` | 从主循环启动测试 ROM |
| `h` | 从主循环返回 launcher |
| `r/l/u/d` | 模拟按住方向 250ms |
| `a/b` | 模拟 A/B 250ms |
| `t/s` | 模拟 Start/Select 250ms |
| `m/o` | 打开游戏菜单/设置 |
| `v` | 显示红绿蓝色条，任意按键或 g/h 结束 |
| `c` | 只读并打印 TF 根目录的 crash.log |
| `e` | 播放 2 秒 440Hz PCM 测试音，然后恢复原音量 |

串口注入键与触摸键通过按位 OR 合并。串口只辅助验证；实体触摸及 BOOT 始终保留。
应用切换命令由输入任务暂存、主循环执行，避免在输入任务里卸载还在使用的 TF。

## 这次实机遇到的两个显示问题

1. **背光亮但没有像素**：CS 在 SPI 初始化前就拉低，时钟引脚复用及空闲电平
   变化可能被屏幕采样。现在保持 CS=1，先完成一次 SPI 事务建立 mode 2 空闲
   电平，再拉低 CS，重新发送有效的软件复位和 ST7789 初始化命令。已与原固件
   做实机对照，修正后用户确认菜单及虚拟按键正常显示。
2. **切换游戏时报 LCD chip deselect failed**：上游先关闭 I2C，再关闭显示。
   本板 CS 接在 I2C 扩展芯片，显示退出仍要写 PCA9557，因此总线必须最后关闭。
   中文注释在 `rg_system.c` 的 `shutdown_cleanup()`，用于理解设备依赖和退出顺序。

## 从 launcher 到 NES 的调用链

```text
launcher/main/applications.c : application_start()
  取得应用分区、"nes"、ROM 路径、是否恢复存档
    ↓
components/retro-go/rg_system.c : rg_system_switch_app()
  update_boot_config() 保存参数，设置启动应用分区
    ↓ rg_system_restart()，有序释放设备后重启
retro-core/main/main.c : app_main()
  rg_system_init() 读启动参数，configNs == "nes"
    ↓
retro-core/main/main_nes.c : nes_main()
  nes_init() → nes_loadfile() → 每帧循环
```

`update_boot_config()` 保存“启动哪个应用、打开哪个文件”，用 `esp_ota_set_boot_partition()`
选择已有固件分区；没有把 `.nes` 烧入 Flash，也没有下载新固件。

在 `nes_main()` 的 `while (true)` 中按顺序找：

1. `rg_input_read_gamepad()` 取得按键，处理菜单。
2. 把 `RG_KEY_*` 转成 `NES_PAD_*`，调用 `input_update(0, buttons)`。
3. `nes_emulate(drawFrame)` 推进一帧，必要时生成画面。
4. `blit_screen()` → `rg_display_submit()` 提交图像。
5. `rg_audio_submit()` 提交音频，并结合耗时决定后续跳帧。

默认 `frameskip=1` 会间隔提交画面；跳过显示仍执行 `nes_emulate(false)`，
游戏逻辑和声音继续推进。因此模拟帧数、图像提交次数和屏幕实际刷新率要分别看。

## CPU、PPU、APU、mapper 各做什么

先读 `nes_emulate()`：它按扫描线推进 CPU 周期、PPU 和 mapper 回调，
一帧结束后调用 APU 生成采样。这些是软件状态和函数，不是给 ESP32 外接了 6502。

| 模块 | 源码入口 | 要理解的数据流 |
|---|---|---|
| 6502 CPU | [cpu.c](../retro-core/components/nofrendo/nes/cpu.c) 的 `nes6502_execute()` | 游戏指令 → 寄存器、内存、周期变化 |
| 内存总线 | [mem.c](../retro-core/components/nofrendo/nes/mem.c) | 按地址分派到 RAM、PPU、APU、手柄和卡带 |
| PPU | [ppu.c](../retro-core/components/nofrendo/nes/ppu.c) 的 `ppu_renderline()` | 图块、精灵、调色板、滚动状态 → 一行图像 |
| APU | [apu.c](../retro-core/components/nofrendo/nes/apu.c) 的 `apu_emulate()` | 游戏写入声音寄存器的状态 → PCM 采样 |
| mapper | [mmc.c](../retro-core/components/nofrendo/nes/mmc.c)、[mappers](../retro-core/components/nofrendo/mappers) | CPU/PPU 地址 → 卡带 PRG/CHR bank，部分还管理中断 |
| 手柄端口 | [input.c](../retro-core/components/nofrendo/nes/input.c) | 保存按键，模拟 `$4016/$4017` 串行读取 |

切换 mapper bank 后，同一个 CPU 地址可读到不同 ROM 内容，从而使用更大的卡带数据。
`rom_loadmem()` 从 iNES 头读 mapper 编号，`nes_insertcart()` 经 `mmc_init()` 选实现；
源码中有该 mapper，并不证明使用它的全部游戏都完全兼容。

自编 ROM 使用 mapper 0，适合入门。读 [make_nes_demo.py](../tools/make_nes_demo.py)，
观察 16 字节文件头、6502 程序和 CHR 图案，再对照
[test_nes_demo.c](../tests/test_nes_demo.c) 看主机如何用真实模拟核心验证移动和声音。

## 从触摸坐标到手柄位掩码

```text
触摸芯片 → szpi_read_touch()：I2C 0x38，最多两个触点
  → szpi_touch_decode()：事件、坐标解码与旋转
  → szpi_touch_keys_at()：按钮命中，生成 RG_KEY_* 位掩码
  → rg_input_read_gamepad_raw()：合并触摸、BOOT、串口注入
  → input_task()：按下/释放滤波，更新 gamepad_state
  → nes_main()：转成 NES_PAD_*，input_update(0, buttons)
  → 游戏通过模拟的 $4016 读出手柄
```

对照 [szpi_touch.c](../components/retro-go/targets/szpi-esp32s3/szpi_touch.c) 与
[rg_input.c](../components/retro-go/rg_input.c)。本板横屏坐标为 `x=raw_y`、
`y=240-raw_x`，边缘值有检查和钳位。按位 OR 合并多个键，例如
`RG_KEY_RIGHT | RG_KEY_A` 同时表示右和 A；按位 AND 判断某键是否按下。

方向盘四角产生斜向，中心为空区；矛盾的左右、上下会清除；最多两个触点。
`szpi_touch_overlay_row()` 只改发送缓存，所以存档截图不含虚拟手柄。
任务约每 10ms 循环，还受 I2C、滤波和游戏取样影响，不能据此认定实际触摸延迟。

## LCD 像素、I2C 扩展和 DMA 的关系

PCA9557 地址为 `0x19`：IO0 控制 LCD CS，IO1 控制功放，IO2 控制摄像头掉电。
所以屏幕走 SPI，但片选依赖 I2C。`pca_output` 保存输出状态，更新某位时保留其余位，
避免开功放时改变屏幕片选。前面黑屏复盘中的时钟边沿解释来自源码与实机对照，
尚没有逻辑分析仪波形证据。

像素路径是 `PPU 索引色 → 调色板/RGB565 转换与缩放 → LCD 中转缓冲 → SPI → ST7789`。
`lcd_set_window()` 用 `0x2A/0x2B/0x2C` 设置列、行和开始写像素；RGB565 每像素 16 位，
发送字节顺序也要匹配。GPIO42 背光 PWM 独立于像素通信。

## TF 的 MBR、BPB 与这次 1 个扇区兼容

```text
fopen("/sd/roms/nes/游戏.nes") / fread()
  → ESP-IDF VFS → FatFs：文件名、目录、FAT 簇链
  → partition_read()：分区内相对扇区
  → szpi_partition_map()：检查边界，加分区起始 LBA
  → sdmmc_read_sectors() → SDMMC 1-bit → TF
```

`szpi_storage.c::mount_once()` 先初始化 SDMMC（CLK47、CMD48、D0=21），
读整卡第 0 扇区。若是无分区表 FAT 卷就直接验证，否则解析 MBR 并逐个读取启动扇区。
`szpi_partition.c` 的四个入口分别负责：

- `szpi_mbr_scan()`：检查最多四个主分区的起点/长度，拒绝越界、重叠及 GPT 保护表项。
- `szpi_fat_probe()`：检查 BPB 的扇区大小、每簇扇区数、FAT 容量、根目录等，按簇数判定 FAT 类型。
- `szpi_partition_choose()`：多分区选最大的有效 FAT32；仅一个分区时也可选 FAT16。
- `szpi_partition_map()`：每次读写都检查范围，再计算整卡扇区号。

64GB 卡此前在 BPB 校验阶段失败，尚未到 `f_mount()`；统一的 FAT32 提示不能证明需要格式化。

该卡第 3 分区的 MBR 长度是 `122638335` 扇区，BPB 卷长度却是 `122638336`，
相差一个 512 字节扇区；每簇 64 扇区。计算逻辑为：

```text
管理区扇区数 = 保留扇区 + FAT 份数 × 每份 FAT 扇区 + FAT16 固定根目录扇区
数据簇数     = 向下取整((BPB 总扇区数 - 管理区扇区数) / 每簇扇区数)
完整簇区末端 = 管理区扇区数 + 数据簇数 × 每簇扇区数
```

该卡完整簇区末端是相对扇区 `122638299`（不包含末端），仍在 MBR 分区内。
多记的扇区落在不足一个簇的无用尾部，修复仅接受这种 FAT32 情形。
`sector_count` 保持 MBR 原长度，底层不放宽写边界，也不修改卡的 BPB。
多记两个扇区、截断完整簇、FAT16 越界仍拒绝；规则按几何结构判断，不只针对 64GB。
实卡数据与反例在 [test_szpi_partition.c](../tests/test_szpi_partition.c)，
实机挂载和游戏运行证据在 [VALIDATION_SZPI.md](../VALIDATION_SZPI.md)。

## ES8311：I2C 配置与 I2S 数据要分开看

```text
游戏写 APU 寄存器 → apu_emulate() → 16 位双声道 PCM
  → rg_audio_submit() → driver_submit() / esp_codec_dev_write()
  → I2S0 + DMA → ES8311 DAC → 功放 → 喇叭
```

驱动在 [drivers/audio/szpi.c](../components/retro-go/drivers/audio/szpi.c)。I2C 配置 ES8311，
I2S 用 MCLK38、BCLK14、WS13、DOUT45 送声音；WS 区分声道，BCLK 推进位，MCLK 提供工作时钟。
采样率 32000 与游戏帧率不同，双声道 16 位有效数据量为 `32000×2×2=128000` 字节/秒。

重点比较 `driver_init()`、`driver_set_rate()`、`driver_deinit()`：
创建并配置通道 → 开启 I2S → 打开 codec → 提交 PCM → 关闭 codec → 删除资源。
当前 codec_dev 1.3.6 的格式设置会先停止通道，调用前需让通道处于运行状态，并保持 MCLK。
`tx_started`、`codec_open` 记录状态，避免关闭时重复停通道。这是此前无声故障的重要修复。

静音先关功放；恢复时先解除 DAC 静音，再打开 PCA9557 IO1 控制的功放。
串口 `e` 绕过 NES APU 直接播放 PCM，能帮助区分游戏产声问题与硬件输出链路问题；
直接测试音可听到之后，还要验证游戏 A 键的声音。

## FreeRTOS、双缓冲和 DMA 的知识点

CPU/PPU/APU 在同一主循环按模拟时间推进，后台任务通过状态和消息配合：

| 执行位置 | 入口 | 数据和等待点 |
|---|---|---|
| 游戏主循环 | `main_nes.c::nes_main()` | 读按键、模拟一帧、提交图像与音频 |
| 输入任务 | `rg_input.c::input_task()` | 更新 `gamepad_state`，约 10ms 轮询 |
| 显示任务 | `rg_display.c::display_task()` | 从消息取得图像指针，缩放后发给 LCD |
| 监测任务 | `rg_system.c::system_monitor_task()` | 周期统计运行状态 |

`rg_task_create()` 最终调用 `xTaskCreatePinnedToCore()`。`rg_display_submit()` 传图像指针，
不会复制整帧；双缓冲和 `rg_display_sync()` 防止提前改写显示任务正在读的数据。

LCD 中转缓冲是 `320×4×2=2560` 字节，以 `MEM_DMA` 分配。
`lcd_send_buffer()` 发起颜色 DMA 后用 `lcd_sync()` 等待完成，再复用同一缓冲。
DMA 只负责搬运，CPU 仍需准备数据，并遵守内存能力和生命周期要求。
I2S 另有自己的 DMA 配置，不存在启用一个 DMA 就包办全工程的情况。

## 构建、烧录和验证怎么区分

在仓库根目录 PowerShell 中执行：

```powershell
# 触摸、分区和真实 Nofrendo 核心的主机测试。
.\test-szpi.ps1

# 编译两个应用，并打包完整镜像。
.\build-szpi.ps1 -Action build-img

# 烧录已经生成的完整镜像。
.\build-szpi.ps1 -Action flash -Port COM5

# 查看串口；监视器与烧录工具不能同时占用该端口。
.\build-szpi.ps1 -Action monitor -Port COM5
```

`flash` 使用已有镜像，改源码后先 `build-img`；COM5 与 IDF 路径是本机设置。
完整镜像从 `0x0` 写入，`retro-core.bin` 属于 `0x210000` 应用分区，不能互换。
根目录 `partitions.csv` 是上游编译占位表，布局以打包镜像及验证脚本为准。

[check_szpi_image.py](../tests/check_szpi_image.py) 检查镜像、分区和 VS Code 烧录元数据。
主机测试证明相应代码路径；编译证明能生成固件；烧录校验证明字节写入；
最终还需实机画面、触摸、声音验收。已完成的硬件证据和未覆盖范围见验证记录，
不能把某款 ROM 的运行结果推广到全部游戏。

## 按顺序做六个小练习

1. **画输入链。** 从 `szpi_read_touch()` 连到 `$4016`，标明每层数据格式。
   验收：能解释坐标转换与 `NES_PAD_*` 转换为何位于不同文件。
2. **手算扇区边界。** 用实卡数字求相对末扇区，构造末扇区读 1 个和读 2 个的请求，运行分区测试。
   验收：说明允许 BPB 多记 1 个尾部扇区，为什么不允许多写 1 个扇区。
3. **移动一个虚拟按钮。** 在独立 Git 分支调整 A 区域定义，先跑触摸测试，再实机核对。
   验收：画出的按钮与点击区域一致，松手能释放，其他键仍正常。
4. **修改自己的测试图案。** 复制 `make_nes_demo.py` 做实验，先改副本中的 ROM 和 C 输出路径，
   再改图案并生成。原脚本会写两个固定路径。验收：说明 iNES 头、PRG、CHR 的作用，原文件保留。
5. **比较音频路径。** 先用串口 `e`，再按测试 ROM 的 A。
   验收：能列出后者比前者多经过哪些函数，并据此缩小无声故障范围。
6. **保存、恢复、返回。** 在自编 ROM 中保存，移动，再加载，最后返回 launcher。
   验收：日志出现保存和恢复成功，并能解释退出时为什么最后关闭 I2C。
